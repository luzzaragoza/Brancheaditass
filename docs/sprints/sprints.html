Reglas del juego

Lo que dice la sección 2 del CLAUDE.md, más lo que cambió con el boceto del 5/10. Si algo de acá cambia, se cambia primero en el CLAUDE.md.

Un turno: mostrador → depósito → mostrador

  1. Mostrador: llega un visitante. Deja un químico (tipo y si necesita frío o calor) o vuelve a buscar uno (tipo y temperatura).
  2. La jugadora toca Ir al depósito.
  3. Depósito: para dejar, hace clic en el estante donde va; para retirar, hace clic en el químico que entrega.
  4. El modelo valida. Si está bien, pasa el turno y vuelve al mostrador con el próximo pedido. Si no, va a la pantalla final con el motivo.

Químicos y depósito

Cuatro tipos, ni uno más: Acido, Base, Inflamable y Oxidante.

Frío: una heladera con tres estantes, H1, H2 y H3. Calor: al lado, los estantes E1, E2 y E3. Cada uno tiene 4 lugares.

En el código siguen siendo 6 Contenedor: 3 Heladera y 3 Estante. En pantalla los de la heladera también se ven como estantes.

Guardar en el lugar de la temperatura equivocada es jugada inválida.

Compatibilidad: se compara solo contra el último

Antes de guardar, el químico nuevo se compara contra el último guardado en ese estante (el de más atrás). Si cada guardado anterior se validó, el resto de la fila ya está bien.

Último \ NuevoAcidoBaseInflamableOxidante
AcidoSe pudrenExplotaVaVa
BaseExplotaSe pudrenVaVa
InflamableVaVaSe pudrenExplota
OxidanteVaVaExplotaSe pudren

Truco para acordarse: hay dos grupos, {Inflamable, Oxidante} y {Acido, Base}. Solo se puede alternar entre grupos: nunca dos del mismo grupo pegados, nunca dos iguales.

La cola de cada estante

El químico nuevo siempre entra al final (última posición ocupada + 1). Nunca en un hueco del medio.

Cuando se saca uno del medio, los de atrás se corren hacia adelante para tapar el hueco.

No es un bug: al correrse pueden quedar pegados dos incompatibles, y explota. Retirar es una jugada riesgosa.

Retiros Decidido

El pedido es un tipo y una temperatura, y vale cualquier químico que coincida en las dos cosas.

Si saca otro químico, pierde. Si lo que queda pegado al correrse la cola es incompatible, también pierde.

Decidido y programado en Juego: quien retira es un visitante que antes dejó ese químico, y el retiro sale de la lista de pendientes. Si no queda ninguno de ese tipo y esa temperatura en el depósito, se pierde en ese momento.

Canje Decidido

Cuando un estante está lleno aparece el botón Canjear. Es opcional.

Canjear vacía ese estante y suma +40 fijos. No gasta el turno.

Lo canjeado ya no se puede entregar: si después vuelven a buscar algo que estaba ahí, se pierde. No es un bug.

Mejores puntajes Decidido

Los 5 mejores de esa computadora: iniciales de 3 letras, puntaje y turno. Si la partida entra en el top 5, la pantalla final pide las iniciales.

Propuesto: se guardan en puntajes.txt, al lado del juego, una línea por puesto (LUZ;340;31). Si el archivo no existe o falla, la tabla arranca vacía y se sigue jugando. Consultarlo con el profe antes de programarlo.

Perder siempre explica por qué

Los motivos los arma el modelo y nombran el estante con su código, como se ve en pantalla (H2, E1).

Git con GitHub Desktop (o desde IntelliJ)

Desde IntelliJ: Ctrl+T trae lo de GitHub (hacerlo siempre antes de empezar y después de tocar algo en la web), Ctrl+K hace el commit y Ctrl+Shift+K el push. La rama se cambia con el nombre que aparece arriba a la izquierda (o abajo a la derecha). Si GitHub no te deja subir una rama, no hagas un fork: pedile a Luz que te agregue como colaboradora.

  1. Crear el proyecto (lo hace una sola). En IntelliJ, crear el proyecto Java (guía de IntelliJ, paso 1).
  2. Convertirlo en repositorio y publicarlo (la misma). En GitHub Desktop: File › Add local repository, elegir la carpeta del proyecto y aceptar crear un repositorio ahí. Crear un archivo .gitignore con estas líneas, para no subir archivos de cada computadora: out/ y .idea/workspace.xml. Hacer el primer commit y tocar Publish repository.
  3. Invitar y clonar. En github.com, en el repositorio: Settings › Collaborators › Add people, y agregar a las otras tres por su usuario. Cada una acepta el mail de invitación y en GitHub Desktop hace File › Clone repository, pestaña GitHub.com, elige el repositorio y una carpeta. Después lo abre en IntelliJ con File › Open.
  4. Una rama por tarea. Antes de empezar, en GitHub Desktop: Current Branch › New Branch, con un nombre corto que diga la tarea (por ejemplo, contenedor). Siempre crearla desde main actualizado.
  5. Commit. Cuando algo compila y funciona, en GitHub Desktop aparecen los archivos cambiados a la izquierda. Escribir abajo un resumen corto ("Contenedor: guardar y sacar") y tocar Commit to la rama. Después, Publish branch la primera vez y Push origin las siguientes.
  6. Pull request. Tocar Preview Pull Request y después Create pull request: se abre GitHub. Escribir qué hace el cambio y cómo probarlo, y en Reviewers elegir a la revisora de la tabla.
  7. Revisar (la revisora). En el pull request, pestaña Files changed: leer cada archivo con la lista "Qué mirar en cada revisión". Comentar en la línea lo que haya que cambiar. Cuando está bien: Review changes › Approve.
  8. Mergear. Con la aprobación, la dueña toca Merge pull request en GitHub. Nada entra a main sin aprobación: GitHub Desktop no lo impide, es un acuerdo del grupo.
  9. Traer lo de las demás. Para actualizar main: pasar a main en Current Branch, tocar Fetch origin y después Pull origin. Para llevar esos cambios a una rama propia: pasar a la rama y, en Current Branch, Choose a branch to merge into la rama › main.
